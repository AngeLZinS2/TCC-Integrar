# NOVA FUNCIONALIDADE — ADMINISTRADOR DA EMPRESA + INTEGRAÇÃO UNIVERSAL DE DADOS

Você deve implementar e revisar no projeto atual uma nova camada de
"Administrador da Empresa" e um sistema de "Integração Universal de Dados".

IMPORTANTE:

Antes de alterar qualquer código:

1. Analise a arquitetura atual.
2. Analise os modelos existentes.
3. Analise os papéis/permissões atuais.
4. Analise frontend e backend.
5. Analise as rotas existentes.
6. Analise como Company, User, Sector, Position e demais entidades
   estão estruturadas.
7. Verifique o que já existe e REUTILIZE o máximo possível.
8. NÃO duplique funcionalidades já existentes.
9. NÃO quebre funcionalidades existentes.
10. Execute os testes atuais antes de começar.
11. Depois das alterações, execute novamente os testes.

Não faça uma reescrita desnecessária da aplicação.

==================================================
2. RESPONSABILIDADE DO ADMINISTRADOR DA EMPRESA
==================================================

O Administrador da Empresa deve conseguir configurar toda a estrutura
da própria empresa.

Ele poderá:

- cadastrar RH;
- cadastrar setores;
- cadastrar cargos;
- cadastrar gestores;
- configurar unidades;
- configurar informações da empresa;
- configurar regras de usuários;
- configurar integração externa;
- configurar mapeamento de dados;
- testar conexão;
- executar sincronização;
- visualizar histórico da sincronização;
- configurar regras de criação de perfis;
- ativar/desativar sincronização.

IMPORTANTE:

Ele somente pode acessar dados da própria empresa.

Nunca poderá:

- acessar outra empresa;
- acessar dados de outra empresa;
- modificar outra Company;
- alterar configurações de outro tenant;
- visualizar credenciais de outra empresa.

==================================================
3. PLATFORM OWNER
==================================================

O Platform Owner NÃO deve administrar funcionários das empresas.

O Platform Owner deve enxergar somente informações necessárias para
administrar a plataforma SaaS.

Pode visualizar:

- empresas cadastradas;
- empresas ativas;
- empresas suspensas;
- quantidade de colaboradores;
- quantidade de usuários;
- utilização da plataforma;
- métricas agregadas;
- crescimento;
- uso das funcionalidades;
- status da integração;
- saúde geral da conta.

NÃO deve visualizar:

- nome individual de colaboradores;
- e-mail individual;
- CPF;
- telefone;
- data de admissão individual;
- progresso individual;
- documentos pessoais;
- informações pessoais dos funcionários.

A regra é:

PLATFORM OWNER
→ administra a plataforma.

ADMINISTRADOR DA EMPRESA
→ administra a empresa.

RH
→ administra pessoas e processos de RH.

==================================================
8. REGRA ABSOLUTA — BANCO EXTERNO READ-ONLY
==================================================

ESTA É UMA REGRA FUNDAMENTAL DA ARQUITETURA.

A plataforma NUNCA poderá modificar o banco externo.

O banco externo será utilizado SOMENTE para leitura.

Permitido:

SELECT

Proibido:

INSERT
UPDATE
DELETE
DROP
ALTER
TRUNCATE
CREATE
RENAME
GRANT
REVOKE

E qualquer outro comando capaz de:

- criar dados;
- modificar dados;
- excluir dados;
- modificar tabelas;
- modificar estrutura;
- modificar permissões.

==================================================
9. NÃO CONFIAR SOMENTE NO FRONTEND
==================================================

A proteção READ-ONLY não pode existir somente no frontend.

O backend deve bloquear qualquer operação que não seja leitura.

Mesmo que alguém tente manipular a API diretamente:

UPDATE
DELETE
INSERT
DROP

deve ser rejeitado.

Nunca confiar no cliente.

==================================================
10. NÃO PERMITIR SQL ARBITRÁRIO
==================================================

O Administrador NÃO deve receber um campo para executar SQL livre.

Não permitir:

"Digite qualquer SQL"

O sistema deve trabalhar através de consultas estruturadas.

O usuário seleciona:

- tabela;
- campo;
- relacionamento;
- filtro;

e o sistema constrói consultas de leitura.

==================================================
11. UMA ÚNICA CONSULTA DE LEITURA
==================================================

Não permitir múltiplos comandos.

Exemplo:

SELECT * FROM funcionarios;
DELETE FROM funcionarios;

DEVE SER REJEITADO.

Não permitir SQL concatenado.

O Connector deve trabalhar exclusivamente com operações de leitura
controladas.

==================================================
12. CREDENCIAL READ-ONLY
==================================================

Durante a configuração:

RECOMENDAR e, quando tecnicamente possível, VALIDAR que o usuário
externo utilizado tenha somente permissão SELECT.

Exemplo:

integration_readonly

Permissão:

SELECT

Sem:

INSERT
UPDATE
DELETE
DROP
ALTER
CREATE
TRUNCATE

IMPORTANTE:

Mesmo que o cliente forneça uma conta com mais permissões, o sistema
não deve utilizá-la para operações de escrita.

A plataforma deve continuar aceitando somente operações de leitura.

==================================================
13. SEGUNDA CAMADA DE PROTEÇÃO
==================================================

O Connector deve possuir uma camada própria de proteção.

Antes de executar uma consulta:

1. validar;
2. identificar a operação;
3. permitir somente leitura;
4. rejeitar qualquer operação de escrita.

Exemplos:

SELECT * FROM funcionarios
→ PERMITIDO

UPDATE funcionarios SET nome = 'X'
→ BLOQUEADO

DELETE FROM funcionarios
→ BLOQUEADO

DROP TABLE funcionarios
→ BLOQUEADO

INSERT INTO funcionarios
→ BLOQUEADO
